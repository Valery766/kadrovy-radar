# Проверка API Кадрового радара

Команда unecon.tech. Базовый адрес: https://radar.digital-projects.tech. Контракт: `openapi.yaml` (OpenAPI 3.1). Воспроизводимые проверки и параметры: `DATA-API.yaml`, `TEST-DATA.json`.

API обслуживает мини-приложение MAX и является частью решения. Оно не требует отдельной учетной записи продукта. Для чтения публичных данных доступна штатная демо-сессия; публикация и отклик выполняются пользователями MAX после проверки данных запуска сервером.

## Без изменения вакансий и откликов

1. Выполнить `GET /api/health`. Ожидается HTTP 200 и `ok: true`.
2. Выполнить `POST /api/session` с JSON `{}`. Ожидается HTTP 200, `user.demo: true` и сессионный `token`. Значение хранить только на время проверки. Оно не является токеном бота.
3. Добавить заголовок `Authorization: Bearer <полученный token>` и выполнить `GET /api/bootstrap`, `GET /api/jobs?limit=12&offset=0`. Ожидается HTTP 200, справочники и каталог без контактов/ответов кандидатов.
4. Из результата каталога выбрать `jobs[0].id`, выполнить `GET /api/jobs/<id>`. Ожидается карточка с текстом, без приватных контактов.
5. Проверить поиск `GET /api/jobs?q=повар&region=78&minSalary=60000`. Ноль результатов допустим: записи могут закрываться и фильтроваться.
6. `GET /api/jobs` без Authorization возвращает 401; `limit=0` с сессией возвращает 400; несуществующий идентификатор карточки возвращает 404.

Последовательность не создает вакансий, откликов или сообщений. Выдача демо-сессии не создает аккаунт в базе. Тяжелые расчеты не входят в этот автоматический проход: `POST /api/market` сохраняет карточку, а внешние источники могут быть временно недоступны.

## Основной сценарий с двумя ролями

Работодатель и кандидат открывают https://max.ru/t796_hakaton_max_bot с разных реальных аккаунтов. Мини-приложение получает `window.WebApp.initData` от MAX и отправляет ее в `POST /api/session`. Сервер проверяет подпись и выдает сессию на 12 часов. Тестовые пароли MAX, рабочие токены бота и общая сессия команды для этого не нужны.

Работодатель рассчитывает карточку, задает 83000, подтверждает текст и публикацию. Кандидат находит эту учебную вакансию, отвечает на вопросы, отмечает согласие и откликается. Работодатель видит ответ и отправляет приглашение. По согласованному учебному отклику можно проверить «Нанят»: вакансия закрывается. Результат доставки необходимо проверить на стороне второго аккаунта, а не только по HTTP-ответу.

Все изменяющие методы описаны в `openapi.yaml`, параметры основного сценария в `DATA-API.yaml` помечены `manual_in_max`. Их не следует массово запускать на действующих вакансиях. Для дополнительной проверки API токен своей сессии можно увидеть в сетевом ответе `POST /api/session` DevTools после штатного входа. Не передавайте его другому человеку и не включайте в архив.

30.09.2026 команда сообщила об успешной проверке бота с двумя реальными аккаунтами. Это подтверждение команды; здесь не приводится отдельный автоматический протокол той ручной проверки.

## Локальный запуск

В Docker с `MAX_UPDATES_MODE=none` доступны API и интерфейс, а интеграция отправки MAX отключена. На токене действующего бота нельзя одновременно запускать второй webhook/polling-обработчик: он помешает живой версии. Полный сценарий передачи сообщений проверяется в выданном боте по ссылке выше.

Все ошибки API возвращаются JSON. Лимиты тяжелых расчетов: 6 запросов за минуту на пользователя MAX, 3 за минуту на IP демо, до 4 параллельных расчетов на процесс. Демо-сессии: до 20 за минуту на IP. При 429 подождите минуту. При 503 повторите позже и проверьте доступность источника.
